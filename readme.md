# An Interactive Ellis Wormhole Simulation

---

## Basic Usage

1. Go to the [release page](https://github.com/nyasyamorina/wormhole/releases) and download `wormhole-windows-x86_64-pack.tar.xz` (for Linux users, it is `wormhole-linux-x86_64-pack.tar.xz`).

2. Extract the archive to any folder and run `wormhole.exe` (for Linux users, it is `wormhole`).

    Linux users need to have glfw3 installed on system.

---

## System Requirements

- Compatibility with glfw 3.4 and Vulkan 1.3 (a computer with a graphics card driver updated after 2022).

## Controls

- Move the camera: Move the mouse.

- Move (accelerate): `WASD` forward, left, back, right; `ctrl` down; `space` up.

- Adjust the thrust: Mouse wheel.

- Exit: `q`.

## Numerical Values

When the program is opened in the command-line terminal, a series of values ​​will be shown:

- `wormhole radius`: The radius of the wormhole. The entire wormhole is a sphere surface, but its center is not in spacetime.

- `time`: The time elapsed for the player (you).

- `distamt time`: The time elapsed for a distant observer, it is also the coordinate time.

- `speed toward wormhole`: The radial velocity from the player's perspective toward the wormhole. Due to time dilation or whatever you prefer to call it, this value can exceed the speed of light.

- `angular speed`: The angular velocity, which is the velocity perpendicular to the radial direction.

- `maximum simulation error`: The inherent error in the numerical solution.

## Visual Realism

### Celestial Sphere

- The celestial sphere is assumed to be static and infinitely far from the "player", meaning it remains unchanged regardless of movement or time.

- The celestial sphere is generated by a custom (and poorly visual) algorithm. Stars flicker significantly during movement, and large areas remain dark even when moving near the speed of light.

    Using real-world data for celestial sphere rendering is possible (see [my article](https://zhuanlan.zhihu.com/p/600600997)), but this would make Lilith Games enormous, the program complex, and raise copyright issues.

### Post-Processing

- Bloom: The bloom algorithm is based solely on visual representation, not an accurate physical process. This algorithm is inspired by sonicether's [here](https://www.shadertoy.com/view/lstSRS).

- Auto Exposure: Implemented.

### Numerical Simulation

Both player motion and ray tracing utilize numerical solutions to differential equations, inevitably leading to numerical errors (from finite simulation and floating-point errors). Specifically:

- When the player is too far from the wormhole, the celestial sphere rendering will show discontinuities due to dynamically selected ray step sizes.

## Advanced Usage

The program itself (`wormhole.exe` or `wormhole`) is insufficient to run, external shader files are required, and user can provide custom shaders. Running the program in an empty folder with no arguments will generate the shaders used here (see below).

### Parameters

- `-s="path/to/shaders"` or `--shader="path/to/shaders"`: Specifies the shader folder, the folder must contain the shader files (see below). Defaulting to the current running path.

- `--slangc="path/to/slangc"`: Specifies the slang compiler path (see below). Default: "slangc",

- `-f=<>` or `--fov=<>`: Specifies the field of view (vertical), in degrees. Default: 60.

- `-p=<>` or `--posotion=<>`: Specifies the initial distance from the wormhole, Unit: wormhole radius. Default: 10.

- `--simulation-speed=<>`: Controls the ratio of simulation time speed to real-world time speed. Default: 1.

- `--simulation-sub-steps=<>`: Controls the precision of motion simulation. Higher values ​​result in higher precision but also higher CPU usage. Default: 100.

- `--iter-per-call=<>`: Controls the number of ray tracing calculations performed in `iter_ray` (see below). Higher values ​​result in a more accurate rendering result but also higher GPU usage. Default: 500.

## Shaders

### Files and Compilation

Place the following shaders in the shader folder (`--shader`): `init_ray`, `iter_ray`, `render_ray`, `post_process_1`, `post_process_2`, and `final`.
The program will prioritize using spirv shaders (file extension: `.spv`). If not found, it will look for slang shaders (file extension: `.slang`) and automatically call slangc (`--slangc`) to compile.
If still not found, the program will generate default slang shader files (will generate an additional file without an entry: `utils.slang`).

### Layout

All shaders can access 1 `uniform` structure and 4 image buffers, and the `final` shader can additionally access the swapchain image (the next display frame).

The uniform and image buffer are written in slang as follows:

```slang
[vk_binding(0, 0)] ConstantBuffer<Uniform> uniform;

[vk_binding(0, 1)] RWTexture2D<float4, 1> tex_0;
[vk_binding(1, 1)] RWTexture2D<float4, 1> tex_1;
[vk_binding(2, 1)] RWTexture2D<float4, 1> tex_2;
[vk_binding(3, 1)] RWTexture2D<float4, 1> tex_3;
```

The uniform structure is as follows:

```slang
struct SpaceTimeFrame {
    float4 position;
    float4 axis_x;
    float4 axis_y;
    float4 axis_z;
    float4 axis_t;
};
struct SubFrame {
    float3 axis_x;
    float3 axis_y;
    float3 axis_z;
};
struct Uniform {
    SpaceTimeFrame frame;
    SubFrame sub_frame;
    float2 screen_scale;
    float brightness_scale;
    uint iter_per_call;
    uint mipmap_levels;
};
```

The swapchain image is as follows:

```slang
[vk_binding(0, 2)] [format("rgba8")] RWTexture2D<float4> surface;
```

All shaders must have the following entry function:

```slang
[shader("compute")] [numthreads(16, 16, 1)]
void main(uint3 thread_id: SV_DispatchThreadID) { /* ... */ }
```

### Workflow

Although shaders can be customized, the computation (rendering) workflow is fixed. The following is the workflow sequence and default functionality:

1. `init_ray`: Initializes the ray.

2. `iter_ray`: Solves for (traces) the ray.

3. `render_ray`: Renders the ray into the `[vk_binding(3, 1)]` image.

4. (Fixed stage) Clears `[vk_binding(2, 1)]` and builds the mipmap of `[vk_binding(3, 1)]` within it.

5. `post_process_1`: Applys a Gaussian blur to the mipmap (horizontally).

6. `post_process_2`: Applys a Gaussian blur to the mipmap (vertically).

7. `final`: Renders the final result into the swapped-chain image.

The mipmap layers start from 0 and have a total of `uniform.mipmap_levels` levels. The offset and size of each level are calculated using the following method:

```slang
uint2 mipmapOffset(uint2 extent, uint level) {
    uint2 box_offset;
    if ((level & 1) == 0) {
        box_offset = {extent.x >> (level / 2 + 1), 0};
    } else {
        box_offset = {0, extent.y >> ((level + 1) / 2)};
    }
    uint2 box_extent = {
        ((extent.x - 1) >> ((level / 2) + 1)) + 1,
        ((extent.y - 1) >> ((level + 1) / 2)) + 1,
    };

    uint2 mm_extent = mipmapExtent(extent, level);
    return {
        box_offset.x + (box_extent.x - mm_extent.x) / 2,
        box_offset.y + (box_extent.y - mm_extent.y) / 2,
    };
}

uint2 mipmapExtent(uint2 extent, uint level) {
    return ((extent - 1) >> (level + 1)) + 1;
}
```
